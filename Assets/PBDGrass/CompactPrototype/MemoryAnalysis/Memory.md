# 当前 Contact Lab 内存分析

2026-10-21，Unity 2022.3.62f2c1 / D3D11 / RTX 3080 Ti。当前 CPU 局部选择与增量交接版本；本轮只做诊断，没有修改运行时代码、场景、碰撞、塑性、烘焙或 LOD 参数。

结论：**GPU Buffer 预留 214.44 MiB；草系统 CPU 数组有效载荷约 973.19 MiB。GPU 压缩没有同步消除 CPU 的整场原始数据镜像。初始化临时对象又将 Mono 堆撑到约 2.87 GiB，导致进程工作集长时间高于存活数据量。**

## 统计范围

- 144×144 米驻留方窗，20736 格，每格 32 根，共 663552 根驻留容量。
- 其中 32768 根进入 XPBD 池；剩余 630784 根为非活动近景的驻留草。这是容量，不是当前相机画出的草数。
- 中景完整范围 52 米，52～64 米过渡；144 米方窗还包含不可见角落和流式保护带，这些格仍占缓存。
- 外围窗口 256 米；只生成程序草，不保存碰撞/倒伏历史。
- MiB=1048576 字节。以下 GPU 数据是去重后的 ComputeBuffer 的 count×stride，**不等于整个进程总显存**；不含 RenderTexture、纹理、Unity/驱动分配粒度、资源暂存及显示交换链。

## GPU：214.44 MiB 的构成

| 用途 | 计算 | MiB |
| --- | --- | ---: |
| 近景 XPBD 节点、预测位置、速度等 | 32768×8×48 B | 12.00 |
| 近景杆段方向、角速度 | 32768×7×32 B | 7.00 |
| 近景运行时塑性 | 32768×7×16 B | 3.50 |
| 近景最终顶点与法线 | 32768×15×24 B | 11.25 |
| 全驻留压缩姿态 | 663552×80 B | 50.625 |
| 全驻留压缩塑性缓存 | 663552×32 B | 20.25 |
| 全驻留草叶根位置、ID 等元数据 | 663552×32 B | 20.25 |
| 边界/过渡完整历史池 | 65536×816 B | 51.00 |
| 外围可见实例缓冲容量 | 1138688×32 B | 34.75 |
| 分类、映射、风状态、格方向、剔除、模板等其余项 | 逐 Buffer 核对 | 3.81 |
| **合计** | **224852832 B** | **214.44** |

按所有权统计：Renderer 54.6746 MiB、Tiered Handoff 53.4872 MiB、Compact Storage 71.5078 MiB、Outer 34.7668 MiB。这个分法与上表用途分法相互交叉，不能重复相加。

近景完整运行时大块合计 **33.75 MiB**；以前提到的约 20 MiB 主要对应节点和方向状态（19 MiB），没有包含最终几何和运行时塑性。全驻留压缩姿态、塑性与元数据合计 **91.125 MiB，每根 144 B**；这也包含近景草在驻留缓存中的记录，不能全部称为“中景专属”。

完整历史池的 51 MiB 拆成节点 24、方向 14、过渡位置偏移 6、过渡旋转 7 MiB。**65536 是预留容量**：本次初始化占用 46592 根，静止 3 秒后占用 28768 根，约等效 22.39 MiB；移动阶段每秒采样的占用为 26624～41792 根。这些是采样值，不是逐帧最坏情况；空闲槽仍然占显存，不能直接依据静止值缩池。

外围实例缓冲也是预留：1024 个 tile 的候选上限为 1138688 根，所以申请 34.75 MiB。当前默认视角实际输出约 5.1～5.2 万根，实例有效数据约 1.56～1.59 MiB，剩余容量不会自动释放。这个上限包含随后被核心范围、距离密度和视锥剔除的候选；不是模拟了 113 万根 XPBD。将外围输出改成分页或更紧的有保证上限，是一个独立的显存改进方向。

## CPU：整场原始数据仍被持有

通过运行时反射检查实际数组长度，按对象引用去重；List/Stack 按底层数组容量计算，bool 按托管数组的 1 字节计。未通过属性读取触发 CPU 世界刷新。下面列的是数组元素载荷，未包含数组头、对象头及资源自身的原生内存。

| GrassBladeData 常驻数组 | MiB |
| --- | ---: |
| 原始杆段 Rods：663552×7×64 B | 283.50 |
| 原始节点 RestNodes：663552×8×48 B | 243.00 |
| 整场顶点 | 113.91 |
| 整场法线 | 113.91 |
| 整场三角形索引 | 98.72 |
| 整场 UV | 75.94 |
| 草叶元数据 | 20.25 |
| 逐节点逆质量 | 20.25 |
| **以上八项** | **969.47** |
| 格位置、世界方向、流式表、模拟池/交接管理等其他已识别数组 | 3.72 |
| **全部已识别常驻数组** | **973.19** |

八项大数组每根草约 1532 B，覆盖整个 663552 根驻留窗口。`GrassBladeData` 在构造时创建并持有它们；即使 Compact GPU 路径只上传一个模板、共享 UV/索引以及近景几何，CPU 数组也没有释放。销毁初始 Mesh 只释放 Mesh 本身，不会清除 `GrassBladeData` 对这些托管数组的引用。

因此，**GPU 上没有恢复中景全量网格，但 CPU 内存里确实还留着整场初始网格与物理模板展开数据**。它们不是中景每帧 CPU 模拟状态；上一轮将 `data.Blades.Length` 改为 `data.BladeCount`，避免了换页时刷新 CPU 镜像，改变的是计算量，没有改变存储量。

本次采样中，CPU 常驻数组从初始化 1020453548 B 到移动后 1020461740 B，只增加 8192 B（集合容量增长）；全场大数组大小不变。局部选择/交接管理的集合不是当前近 1 GiB 内存的主要来源。

## 实测：存活对象、堆容量、进程占用是三个数字

在 D 盘隔离工程运行当前源码，未操作用户已打开的 Unity。测试 780 个完整 60 Hz tick：先静止 3 秒，再以 12 m/s 在 48 米范围内往返 10 秒，保留 12 个碰撞体和 32768 根活动草。相机为 1600×900 HDR、4× MSAA。内存测试在明确检查点主动 GC；这不是帧耗时测试。

| 检查点 | 托管已用 MiB | Mono 堆容量 MiB | 进程工作集 MiB | 进程私有提交 MiB |
| --- | ---: | ---: | ---: | ---: |
| 场景已载入、草尚未初始化 | 4.04 | 约 5 | 422.47 | 633.95 |
| 初始化结束、主动 GC 前 | 2886.26 | 2937.25 | 3638.08 | 4133.93 |
| 初始化后完成 GC | 993.43 | 2937.25 | 3725.55 | 4216.70 |
| 静止 3 秒后 GC | 994.41 | 2937.25 | 3595.62 | 4201.43 |
| 移动 10 秒后 GC | 994.45 | 2937.25 | 3605.74 | 4210.72 |
| 释放草系统与测试 RT，跨回调后 GC | 21.04 | 2937.25 | 3605.75 | 4210.72 |

本次进程峰值工作集 **4006.62 MiB（3.91 GiB）**，由 Windows `GetProcessMemoryInfo` 的累计峰值记录。外部 PowerShell 约 100 ms 采样的进程曲线另存于 Evidence.zip。

这里 994 MiB 是隔离 Editor 的托管已用总量，不是精确的单个组件独占值；其中约 973 MiB 已对应到草系统数组。释放后减少约 973.41 MiB，与数组核算一致。进程工作集还包括 Editor、Mono、原生资源及驱动映射等，不能直接把约 3.52 GiB 全称为草叶有效数据，也不能与 214.44 MiB 直接相加得到物理内存预算。

释放后堆容量及进程工作集仍高，说明本次回收释放了对象，但没有立即把初始化扩张后的全部堆页归还操作系统。这与数组引用泄漏是不同的问题。本次短程往返 GC 后只增长约 0.05 MiB，不显示持续全场数据累积；不是长时间泄漏测试结论。

初始化路径仍使用 `PBDGrassPatch` 整场生成器：第一次生成 663552 个 Body 和完整 Mesh，随后 `GrassWorldLayout.CreatePatch` 为世界身份再次生成 Body 并替换，还再次生成 UV/索引，最后复制成节点、杆段和各类数组。Body 又包含多组数组、约束对象及终结器。这解释了大量临时对象与回收滞后，也解释了为何运行时只需要近景物理池，却能在启动阶段占用数 GiB。

## 建议的调整顺序

1. **先处理 CPU 初始化及持有方式。** 对当前同类型烘焙、Compact 流式路径，直接从少量模板和世界身份生成 GPU 所需数据；不再构造整场 Body/Mesh，也不再保留全场 UV、索引、法线等副本。CPU 诊断读取改为显式、局部、按需展开。八项大数组中除元数据外已有约 949.22 MiB，属于可研究去除的展开存储；具体可节省多少需在实现后验证，不承诺现在即可全删。
2. **再处理外围实例预留。** 当前 34.75 MiB 的分配与约 1.6 MiB 的视角有效输出相差较大，可按 tile 或分段输出组织，保持容量溢出处理与所有相机视角正确。
3. **最后评估中景驻留数据和历史池。** 当前全驻留 144 B/根的成本会随方窗面积增加。可进一步研究格级共享、只对有塑性的格保存持久数据、控制点格式等；历史池则要测快速移动、传送、碰撞和反复跨 LOD 的占用分布，不能为省 51 MiB 破坏交接。

这次不建议因内存数字立即放弃 XPBD 近景或缩小已经接受的中景范围。最明显的 CPU 内存成本来自原型生成器及旧展开镜像，和中景是否逐帧运行 XPBD 并没有直接关系。流式窗口的容量有界，但当前每个驻留窗口的代价仍偏大。

## 证据与限制

- `Memory.json`：45 个 GPU Buffer、78 个 CPU 数组的逐项 count/stride/bytes，以及分阶段内存统计；GPU 逐项和为 224852832 B。
- `Evidence.zip`：最终测试 JSON、Windows 进程采样 CSV、Unity 日志、临时诊断脚本。`Sources.json` 记录被分析源码与场景哈希。
- `GrassMemoryAudit.cs.txt` 仅作复现源文本，不参与用户工程编译。先按 `../CpuOptimization/prepare_cpu.py optimized` 准备隔离工程，再将文本复制到其 `Assets/PBDGrass/ContactProfileTemporary/Editor/GrassMemoryAudit.cs`；设置 `GRASS_MEMORY_OUTPUT`，用 Unity batchmode / force-d3d11 执行 `GrassMemoryAudit.Run`。仅对隔离工程执行。
- 本轮没有调用整场节点/杆段诊断快照；只在内存检查点读取 16 字节外围绘制参数。`GrassTieredHandoff.Snapshot` 若被其他诊断调用，会临时再分配约 **384.75 MiB GPU** 节点/方向输出，并产生对应 CPU 回读数组；这不属于上述日常常驻量。
- 进程测量来自隔离 Editor，不是最终发行 Player 的 RAM/VRAM 保证；数组与 Buffer 的固定布局可直接核算，Editor 总占用不可原样当作 Player 预算。
